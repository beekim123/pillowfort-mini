# 《枕头堡》美术技术方案：代码出图，运行时生成

> 2026-11-06 用户定。写 `美术文档.md`、`art-manifest.json`、美术包之前先读这份；开发接美术时也读。
> 依据：2026-11-05 在画风库做的对比（`style-lab/algo-official/进度记录.md`）——argon 用 p5.js “代码画画”做的 4 个动态案例（`官方做法 → 墨线手绘`）和同一批拆成部件 PNG + rig 的版本（`拆骨骼对比`）。用户看完的结论：**原版明显更好**；拆骨骼版 1 倍 PNG 放大后发糊，线条沸腾只剩 3 张轮换。
> 本方案只管“美术怎么做、游戏里怎么跑”。画风仍是 **水粉颗粒（夜色）**，角色、噩梦、画面布局照 `设计概要.md` 和 `开发文档.md`。

## 0 一句话

**包里放美术代码，加载时在手机上把图画出来，战斗时跑普通精灵。** 只有少数几个重点角色每帧实时画。

| | 以前的做法（外包交 PNG） | 本方案 |
|---|---|---|
| 美术交什么 | 部件 PNG + rig JSON + 整图 | **美术代码**（每个资源一个出图模块 + 共用画笔库），外加预览页 |
| 包体 | 图片，每个角色几十 KB 到几 MB | 只有代码：画笔库约 10–30 KB，每个资源约 7–12 KB（gzip 后） |
| 清晰度 | 按 1 倍出图，手机上放大会糊 | 按这台手机的实际像素现画，永远清楚 |
| 运行 | 精灵 | 绝大部分也是精灵（加载时生成的），和普通 Cocos 游戏一样快 |
| 要不要 OSS | 图多了要放 OSS | 基本不需要（代码必须进包，而且很小） |

和 `方向决策.md` 第 0 节第 3 行的关系：那里定的“算法出图 + 部件 rig + 程序动画，运行时不跑 p5”**保留部件 rig 和程序动画**，改两处：①出图不在外包电脑上做，改成**在玩家手机上做**（所以美术交代码不交 PNG）；②重点角色允许**实时画**。运行时仍然不跑 p5——p5 只是一个外壳，美术代码直接用 Canvas2D 画。

## 1 为什么这样做（实测数据，2026-11-05）

- 原版 4 个案例的画法基本都是 Canvas2D 原生调用，p5 只管启动和循环（977 KB 的 p5 几乎没用到）。每帧 1500–3200 次画图调用，Mac 上 0.2–1.1 ms；手机估计慢 5–10 倍，**每帧实时画同屏只能撑 1–3 个**。
- 把原版提前烘焙成序列帧：每个角色下载 0.7–8 MB、内存 25–200 MB，**不可行**。
- 拆成 1 倍部件 PNG：每个角色 20–50 KB，但手机上放大发糊，用户不满意。
- 结论：**同一种东西画一次、所有同类共用**，成本只跟“有多少种”有关，跟“同屏有多少只”无关；而且在手机上按实际像素画，就不糊。

## 2 四种运行方式（每个资源属于一种）

| 级别 | 怎么跑 | 用在《枕头堡》哪里 | 同屏数量 |
|---|---|---|---|
| **L0 实时** | 每个实例一张离屏画布。**笔触只在沸腾时重画**（每秒 5–8 次），其余帧只靠节点做位移、旋转、缩放；火光、发光这类必须每帧变的小部分可以每帧画 | 绵绵、糯糯、大噩梦；展示场景（纸箱开出、图鉴大图、早安卡） | **最多 3 个**同时实时 |
| **L1 运行时部件 + rig** | 加载时按部件画成小图（每个主要部件画 3 张颗粒沸腾变体），用现有 `Rig.ts` + 计划中的程序动画层（呼吸、弹簧、链式摆、沸腾轮换）动起来；会走的玩偶有正 / 背 / 侧三套部件（2026-11-06 走位） | 玩偶、床头设施、手电筒 | 6 只玩偶 + 设施 |
| **L2 运行时帧动画** | 加载时把每种东西的每个动作画成帧，放进共享图集；同类所有实例共用 | 噩梦（每个梦 4–6 种 + 精英变体）、棉花、羊 | 噩梦 ≤ 40、羊 ≤ 12 |
| **L3 笔刷图 + 粒子 / 着色器** | 加载时生成十几张“水粉笔刷图”（颗粒色块、溅点、笔触、光斑、烟），交给 Cocos 粒子系统和着色器去喷、去动 | 每只玩偶的弹道（`shot_*`：飞的样子、拖尾、打中）、五种属性效果、烘 / 慢 / 冻 / 臭层、手电筒光束、破单位演出 | 几十到几百个，可合批 |
| 背景 | 进这个梦时画一次，之后是静态图 | 每个梦的背景、栅栏 | 1 |
| UI | 普通九宫格和图标，也可以走 L3 / 背景的方式生成 | 页签、面板、按钮、图标 | — |

每个资源在 `art-manifest.json` 里标明级别（见第 5 节）。

## 3 美术代码包：外包交什么

### 3.1 目录

```
art-code/
  kit/                  共用画笔库（水粉颗粒：色块、颗粒、干笔边、暗面、月光、眼睛……）
  palette.json          色族（从画风库 grainy-gouache 的 style.config 来）
  <key>.js              每个资源一个出图模块，key 和 art-manifest.json 一一对应
  preview.html          预览页：用同一份代码在浏览器里看每个 key 的所有动作、所有沸腾变体、不同倍率
  交付说明.md
```

画风库 `style-lab/styles/grainy-gouache/` 现有的出图脚本是 Node 出 SVG 的，**笔法可以照它，但交付的代码要改成 Canvas2D 版**。

### 3.2 每个出图模块长什么样（接口，美术文档可以细化）

```js
export default {
  key: 'nm_closet_eye',          // 和清单一致
  level: 'L2',                   // L0 / L1 / L2 / L3 / bg
  size: [110, 110],              // 设计像素（750 宽）
  anchor: [55, 100],
  // L2：每个动作几帧、几帧每秒、是否循环
  anims: { walk: { frames: 8, fps: 10, loop: true }, hit: { frames: 4, fps: 12 }, burst: { frames: 8, fps: 12 } },
  drawFrame(ctx, anim, i, opt) { /* opt = { seed, boil, scale } */ },
  // L1：部件表（同 Rig.ts 的 parts，但没有 png 路径）+ drawPart；动作照 Rig.ts 的 anims + motion
  // L0：init(state) / update(state, dt, event) / draw(ctx, state, opt)
  // L3 / bg：draw(ctx, opt)
};
```

### 3.3 硬规则

1. **只用 Canvas2D 标准接口**：路径、填充、描边、`clip`、线性 / 径向渐变、`globalAlpha`、`drawImage`（只画自己生成的画布）。**不用** p5、DOM、`filter`、`shadowBlur`、`getImageData / putImageData`、外部图片和字体——微信离屏画布不一定支持，或者太慢。
2. **确定性**：同一个 `seed` + `boil` 永远画出同一张图。不用 `Math.random`，用画笔库自带的随机数。
3. **坐标写设计像素**，生成器传 `scale`（= 手机实际像素 ÷ 750，约 1.4–2），模块自己 `ctx.scale` 后照常画。线宽、颗粒大小按设计像素定，不要按画布像素。
4. **颗粒不要一颗一颗画**：水粉颗粒的颗粒感用画笔库预先生成的一小块“颗粒纹理”（比如 128×128），用 `clip` + `drawImage` 铺上去。几千个小点逐个画是这个画风最大的性能陷阱。
5. **预算**（在预览页里自测并写进交付说明）：
   - 每个模块 gzip 后 ≤ 12 KB，画笔库 ≤ 30 KB；
   - L2 每帧、L1 每个部件：画图调用 ≤ 3000 次；
   - L0 每次重画 ≤ 2500 次；
   - 预览页显示每个 key 的调用次数和生成耗时。
6. **ES module，无依赖**；不改画风库和游戏工程（同 `通用规范/美术通用规范.md` 第 8 节）。**例外**：`preview.html` 是交付物的一部分，美术文档里写明这是允许的。

### 3.4 预览页要能看什么（2026-11-06 改：只看单件）

- 每个 key：所有朝向、所有动作播放、3 张沸腾变体、1× / 1.5× / 2× / 3× 并排；L1 的发射点和出手帧标出来；弹道模块在自己的格子里播飞的样子、拖尾、打中；
- 显示每个 key 的生成耗时、画图调用次数、代码体积；
- 一个“颗粒强度”滑块（调画笔库的总旋钮，美术文档 1.5）和一个灰度开关。
- **不做整屏、不排布局、不做战斗仿真**：东西怎么摆、怎么动、弹道怎么从玩偶飞到噩梦，是设计在画风库（`style-lab` → 美术代码）和开发在游戏里拼的。美术只画东西。

## 4 游戏侧怎么接（给开发）

1. **ArtGen 生成器**：进游戏 / 进一个梦时，按这一关要用的 key 列表，逐个调出图模块画到离屏画布（微信用 `wx.createCanvas()`，H5 用 `document.createElement('canvas')`），拼进共享图集，**按 key 注册成 SpriteFrame**。游戏其他代码照 `资源对接约定` 按 key 取图，不关心图是 PNG 还是生成的；还没生成好的 key 照旧显示占位。
2. **分帧生成**：每帧最多花 8 ms 生成，放在加载界面和空闲时；先生成这一关马上要出场的。
3. **缓存**：生成好的图集写进小游戏本地缓存（`wx.env.USER_DATA_PATH`），用“美术代码版本号 + scale”当缓存名；下次启动直接读，不用重画。美术代码一更新，版本号变，自动重画。
4. **L1**：沿用 `Rig.ts`，部件的 `png` 换成生成好的 SpriteFrame；程序动画层（`设计进度.md` 里计划的 `motion`）照做。
5. **L0**：每个实例一张离屏画布 + 一个精灵；按沸腾节奏重画、更新贴图；同时最多 3 个，第 4 个起退化成 L1 / L2 的样子。
6. **合批**：L1 / L2 / L3 生成的图尽量放进少数几张图集，保证同屏几百个精灵也只有十来次绘制；对象池照 `开发文档.md` 7.3。

## 5 对 `art-manifest.json` 的要求

每一项在现有字段之外加：

| 字段 | 意思 |
|---|---|
| `level` | `L0` / `L1` / `L2` / `L3` / `bg` |
| `code` | 出图模块文件，如 `art-code/nm_closet_eye.js` |
| `anims` | L2：每个动作的帧数、fps、是否循环；L1 / L0：事件名照 `资源对接约定` 第 5 节 |
| `boil` | 沸腾变体数，默认 3 |
| `display` | 在屏幕上大约多大（设计像素），用来定生成尺寸 |

## 6 P1 预算估算（中端手机，scale ≈ 1.5）

| 内容 | 级别 | 估算内存 | 加载时要画几张 |
|---|---|---|---|
| 这个梦的噩梦 5 种（每种约 20 帧，生成 160×160） | L2 | 约 10 MB | 约 100 |
| 棉花 + 羊 | L2 | 约 0.6 MB | 约 16 |
| 玩偶 9 种（每种约 15 个部件 × 3 沸腾变体） | L1 | 约 5 MB | 约 400 个部件 |
| 绵绵、糯糯 | L0 | 约 1 MB | 实时 |
| 大噩梦（打它的时候才有） | L0 | 约 3 MB | 实时 |
| 笔刷图约 20 张 | L3 | 约 1.5 MB | 20 |
| 这个梦的背景 | bg | 约 5 MB（和一张 jpg 解码后一样） | 1 |
| **合计** | | **约 25 MB** | **约 540 张，首次 0.5–4 秒，之后读缓存** |

战斗中每帧真正实时画的只有 L0 那 1–3 个；其余是约 350 个精灵（40 噩梦 + 12 羊 + 12 玩偶的部件 + 特效），合批后在中端安卓 50 帧以上应该没问题。**这些都是估算，要按第 7 节真机验证。**

## 7 风险和要先验证的（放在 P1 开发最前面）

做一个最小验证：**1 只玩偶（L1）+ 1 种噩梦（L2）× 40 只 + 羊 + 1 种打中特效（L3）+ 绵绵（L0）**，在 Cocos 3.8 里接 ArtGen，在 iPhone 和中低端安卓的微信里测：

1. 微信离屏画布画水粉颗粒的速度（尤其颗粒纹理铺法）；
2. 首次生成耗时、缓存读回耗时；
3. 画布 → Cocos 贴图这条路在微信和 H5 都通，L0 每秒 5–8 次更新贴图的开销；
4. 同屏帧率和内存。

不过关的处理：生成太慢 → 减少帧数或沸腾变体、加大缓存优先级；L0 太慢 → 重点角色也降成 L1；颗粒太慢 → 改用着色器叠颗粒。
